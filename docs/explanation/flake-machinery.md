# The flake machinery

How this repo uses flake-parts: one module system running at three layers,
a dendritic substrate beneath the declarations, and a generated
`flake.nix`. The generators' *why* is [the framework's
why](declaration-framework.md); this page is the machinery itself.

## One engine, three layers

The Nix module system — options, config, merging, priorities — runs here
at three layers:

- **flake level** — flake-parts evaluates every file under `modules/` as a
  module of the *flake itself*. Options like `flake.programs`,
  `flake.hosts`, `flake.users`, `flake.modules`, and `flake.factory` live
  here, and their merged values become flake outputs.
- **per host** — NixOS or nix-darwin evaluates a host's module set into
  `nixosConfigurations.<h>` / `darwinConfigurations.<h>`. Options like
  `services.*`, `homebrew.*`, and `hostConstants` live here.
- **per home** — home-manager evaluates each
  `homeConfigurations."<user>@<host>"` independently. Options like
  `programs.*`, `home.*`, and (via read-through) `hostConstants` live
  here.

The same merge semantics apply at every layer, which is what lets the
boundary priority wrapper reason uniformly about any module it is handed.

## The dendritic substrate

Two mechanisms make every `.nix` file under `modules/` a self-contained
feature (`modules/nix/flake-parts/dendritic-tools.nix`):

- **import-tree** — `flake.nix`'s single expression is
  `flake-parts.lib.mkFlake` over `import-tree ./modules`, so every `.nix`
  file below `modules/` is auto-imported as a flake-parts module. Adding a
  feature is adding a file; no import list to maintain. (Corollary: flake
  eval ignores *untracked* files — `git add` new ones.)
- **`flake.modules.<class>.<name>`** — flake-parts' modules option: a
  named registry of deferred modules per class (`nixos`, `darwin`,
  `homeManager`, `generic`). A feature file *contributes* to a name;
  same-name definitions from different files merge. Aspects are how
  features publish importable pieces, and how hand-written features remain
  first-class beside the generated units.

The substrate is machinery, not the way of working: day to day you write
declarations, and the generators produce the aspects. Hand-written aspects
are the escape hatch for what declarations don't cover (services, daemons,
oddballs).

## How the generators attach

Everything under `modules/nix/flake-parts/` is flake-level machinery
riding that substrate:

- `declarations/programs.nix` — declares `flake.programs`; maps each
  declaration to generated `flake.modules` units.
- `declarations/hosts.nix` — declares `flake.hosts`; generates the
  per-host baseline and host-config aspects, applies the boundary priority
  wrapper, and stamps `nixosConfigurations` / `darwinConfigurations` /
  `homeConfigurations."<user>@<host>"`.
- `declarations/users.nix` — declares `flake.users`; resolves each entry
  into per-(user, host) home-manager unit sets, exposed as
  `flake.lib.homeUnits` for the hosts generator to union in at stamping.
- `factory.nix` — declares the `flake.factory` option; the user factory in
  `modules/factory/user/` populates it.
- `dendritic-tools.nix` — the substrate itself (flake-parts, flake-file,
  import-tree inputs and wiring).
- `darwinConfigurations-fix.nix` — declares the
  `flake.darwinConfigurations` option, which nix-darwin ships no
  flake-parts module for.

Each generator is a flake-parts module like any other: it declares an
option, reads its merged value from `config.flake.*`, and writes
`config.flake.modules` / outputs. Declaration files anywhere in the tree
(a program's folder, a host's folder) set the options; import-tree brings
both sides together.

## The generated flake.nix

`flake.nix` is generated by flake-file, never hand-edited. Inputs are
declared where they are used — each feature sets `flake-file.inputs`
(stylix's file declares the stylix input, and so on) — and
`nix run .#write-flake` regenerates `flake.nix` from the merged
declarations. The outputs expression is the single import-tree line above,
declared in `dendritic-tools.nix`.
