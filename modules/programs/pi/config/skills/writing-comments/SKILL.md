# Writing comments

A comment earns its line by saying something a reader cannot recover from the
code, names, types, or signature. Most code needs none. The rules below say
when one exists and what it says; each gives its reason so you can apply it to
cases the examples don't show.

## When a comment exists

Unless the task says otherwise, write a comment for exactly two things:

- why one side of a trade-off was chosen
- why surprising code is right

Everything else is the code's job. A comment that says what the code does is
deleted, not reworded. Why: a what-comment drifts the first time the code
changes, and a reader who trusts it is then misled.

```ts
// Increment the retry count.          ← says what; delete
retryCount++;

// disabled users must never receive notifications   ← says why; keep
const recipients = users.filter((user) => user.enabled);
```

When a comment mixes narration with a reason, keep only the reason.

```sh
# Create the directory before writing because fresh installs lack it.
# → fresh installs lack the config directory
mkdir -p "$config_dir"
```

## How a comment is written

- One line for ordinary prose. A second only for a consequence or removal
  condition.
- Placed beside the exact code it explains; a multi-line comment above it.
- Split a block that covers several steps into small comments beside each
  step; keep a block only when it genuinely spans the whole unit.
- Name real dependencies only. A reusable module describes its own contract,
  not the callers that happen to use it.

```ts
// leaks a consumer the module does not know about
// 30s timeout because the checkout dashboard polls every minute
const cacheTtl = 30_000;

// states the module's own reason
// keep values younger than the minimum supported polling interval
const cacheTtl = 30_000;
```

## Kinds of comment

### Trade-off and rationale
State why the choice exists, in one durable line beside the decision. Omit it
when names and surrounding code already make the reason clear.

```nix
# preserve the upstream binary-cache hit
package = inputs.llm-agents.packages.${system}.pi;
```

### Invariants
Name the condition and what breaks without it. Replace vague warnings
("important", "do not change") with the concrete dependency.

```rust
// Keep sorted.                        → binary search requires key order
entries.sort(compareKeys);

// There can only be one writer.       → concurrent writers can lose updates
let _guard = writer_lock.lock();
```

### Workarounds
Name the external limitation, why the surprising code is needed, and the
removal condition when known. Leave out transient error text.

```ts
// Safari ignores focus until the next paint; remove when the polyfill lands
requestAnimationFrame(() => input.focus());
```

### Doc comments
Every public item gets one, and an internal item gets one when its signature
and body do not make it obvious. A doc comment states what the signature
cannot: units, ownership, lifecycle, side effects, errors, ordering, edge
cases. It may describe what the item does, but it repeats no name or type.
When the signature is the complete contract, write nothing.

```rust
/// Gets a user by ID.                       ← repeats the signature; delete
fn user(id: UserId) -> User

/// Leaves environment references unresolved for the caller.   ← contract
fn parse(path: &Path) -> Result<Config, Error>
```

```python
def borrow_connection() -> Connection:
    """Return a pooled connection that the caller must release."""
```

### Structural markers
A dashed-rule section label marks a substantial logical part of a file or a
long function. Arrange/act/assert (or Given/When/Then) markers may stand in
tests. Labels on every small block are narration; delete them.

```nix
# ------------
# Registry construction
# ------------
```

### Task markers
Follow the project's tracker convention for deferred work; record the item
there and keep a local `TODO` only when that convention requires one. A
`HACK` that explains compatibility code is a workaround comment and follows
that rule.

## Kept verbatim

- Machine-readable directives (`eslint-disable-next-line`, `shellcheck
  disable=`, `noqa`, `#[allow(...)]`). Any human reason sits in a separate
  comment.
- Licence headers, copyright notices, SPDX identifiers, and generated-file
  markers (`Code generated by … DO NOT EDIT`). Change them only when the task
  is about licensing, ownership, or the generator.

## Deleted

- Commented-out code, old implementations, and debug statements. Version
  control keeps them. A caller-facing usage example inside a doc comment is
  documentation, not disabled code.

## Decision points

- Reason versus invariant: a reason explains a choice; an invariant names a
  condition that must stay true. Write whichever the reader needs to change
  the code safely.
- Doc comment versus none on an internal item: write one when a reader would
  otherwise open the body to learn how to call it.
